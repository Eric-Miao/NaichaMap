# 上海奶茶地图 V1 设计文档

日期：2026-10-26

## 1. 产品意图

这个产品帮助人在上海逛街或游玩时，快速回答两个问题：

1. 我当前所在的商场里有哪些奶茶、饮品和咖啡店？
2. 如果我不在商场，一公里内有哪些这类门店？

第一版面向产品发起人和少量朋友测试。它优先验证门店发现体验，而不是导航、交易、社交或商业化能力。

## 2. 已确认的目标

- 仅覆盖上海，但目标是上海任意地点按需冷启动，不限定少数试点商场。
- 移动端优先。
- 获取用户当前位置后，优先识别当前商场。
- 能确认当前商场时，优先展示该商场内的奶茶、饮品和咖啡店。
- 不能确认当前商场时，展示当前位置一公里内的相关门店，并将能够确认商场归属的门店按商场聚类。
- 门店按距离排序，并提供“全部 / 茶饮 / 咖啡”分类。
- 门店提供复制品牌名功能，方便用户前往微信搜索。
- 地图数据和交互结果可按需写入 Supabase，减少后续重复查询。
- 普通用户无需登录即可提交纠错。
- 同一 IP 每五分钟最多提交一次纠错。
- 管理员直接在 Supabase 后台处理门店和纠错，不开发独立管理后台。

## 3. 非目标

第一版不做：

- 路线规划与导航。
- 楼层、铺位号和室内地图浏览。
- 微信小程序跳转。
- 普通用户账号、收藏、评论或社交功能。
- 独立管理员后台。
- 上海以外城市。
- 订单、支付、优惠券或商业推广。
- 对所有门店数据绝对完整和实时的承诺。

## 4. 失败标准

即使技术上可以运行，出现以下任一情况也视为第一版失败：

- 用户打开页面后不能在数秒内理解附近有哪些饮品店。
- 商场内门店被周边街铺淹没，无法体现“当前商场优先”。
- 门店分类大量混入普通餐厅。
- 页面强制注册或要求过多权限才能浏览。
- 纠错可以直接污染正式门店数据。
- 为节省接口调用而保存精确用户位置。

## 5. 授权与合规前提

产品发起人已确认持有高德的邮件许可，允许在本项目环境中：

- 将高德查询结果持久化到 Supabase；
- 使用 MapCN 或其他第三方地图组件渲染相关数据。

该邮件本身不进入代码仓库。项目发起人负责保存原始邮件及附件。实现和部署不得超出邮件许可限定的项目、环境、用途、期限、字段和调用方式。若许可条件变化，缓存与展示逻辑必须随之调整。

建设者默认决策：除非许可明确允许且产品确有需要，不保存完整高德原始响应，只保存 V1 展示、去重、刷新和商场归属所需的规范化字段。

项目发起人确认：当前邮件许可没有额外规定可保存字段、缓存期限、仅限测试环境、授权到期时间或调用量限制。因此 V1 可以持久化上述规范化结果。若后续收到补充条件，再按新条件限制字段、调整有效期或清理历史数据。

## 6. 已考虑的实现路线

### 路线 A：完全动态查询高德

每次打开页面都调用高德，不持久化 POI。

- 优点：简单，数据相对新。
- 缺点：重复调用多，响应依赖外部接口，无法形成可人工修订的门店库。

### 路线 B：MapCN + 开放数据和用户贡献

以 OpenStreetMap、Wikidata 和用户提交作为数据来源。

- 优点：可合法形成长期自有数据，MapCN 集成自然。
- 缺点：上海商业门店覆盖不完整，无法满足“到商场后快速看全”的核心体验。

### 路线 C：高德按需查询 + Supabase 持久化 + MapCN 渲染

先查询本地数据库，缺失或过期时调用高德，将获得许可的字段规范化后写入 Supabase，再由 MapCN 展示。

- 优点：兼顾覆盖率、速度、接口成本和人工修订能力。
- 缺点：需要处理坐标系、去重、过期刷新和授权边界。
- 选择：采用路线 C，因为项目发起人确认已有覆盖存储与混用场景的邮件许可。

## 7. 技术架构

### 7.1 前端

- React + TypeScript。
- 采用适合 Vercel 的 React 全栈框架，具体稳定版本由实现计划确定。
- Tailwind CSS 与 shadcn/ui 构建界面。
- MapCN / MapLibre 渲染地图、门店标记和当前位置。
- 浏览器 Geolocation API 获取用户坐标。

### 7.2 服务端

- Vercel 承载页面和服务端 API。
- 服务端持有高德 Web Service Key 与 Supabase Secret Key。
- 浏览器不直接获得任何服务端密钥。
- 附近搜索、缓存刷新、数据合并、纠错限流都通过服务端接口完成。
- Vercel 服务端通过 `supabase-js` 和 Supabase HTTPS Data API / RPC 访问数据库，不把 PostgreSQL 直连作为网页运行时依赖。
- PostgreSQL 直连仅用于迁移、备份和维护；建设阶段优先使用 Supabase MCP、CLI 或控制台 SQL Editor。

### 7.3 数据库

- Supabase PostgreSQL。
- 启用 PostGIS，用于一公里范围检索、距离排序和商场范围判断。
- 正式数据通过服务端访问；客户端不拥有写入正式门店表的权限。

### 7.4 部署

- 网页与 API：Vercel Hobby。
- 数据库：Supabase 免费套餐。
- 第一版是个人、非商业测试用途。

## 8. 坐标约定

- 浏览器定位和 MapCN 底图采用 WGS84 坐标。
- 高德接口使用 GCJ-02 坐标。
- 每条高德门店和商场记录保存 GCJ-02 原始坐标及转换后的 WGS84 坐标。
- 调用高德前将用户坐标转换为 GCJ-02；地图展示和 PostGIS 查询统一使用 WGS84。
- 原始坐标与转换坐标分字段保存，禁止混用。

## 9. 核心数据流

### 9.1 附近门店查询

1. 用户允许定位后，浏览器把本次经纬度发送给服务端。
2. 服务端不持久化用户精确经纬度。
3. 服务端根据坐标确定一个粗粒度查询网格，并查看该区域是否有未过期的抓取记录。
4. 如果数据未过期，从 `stores` 通过 PostGIS 查询一公里内门店。
5. 如果区域从未查询或已过期，服务端把坐标转换为 GCJ-02，调用高德周边搜索。
6. 服务端只保留奶茶、饮品和咖啡相关结果，排除普通餐厅。
7. 结果按高德 POI ID 去重并写入或更新 Supabase。
8. 服务端将数据库结果转换成统一响应，按距离排序后返回前端。

### 9.2 商场优先

1. 已确认的商场边界包含用户坐标时，可判定用户位于该商场。
2. 没有边界时，只有高德父级 POI 明确指向同一商场，且附近商场结果与地址信息一致，才可判定当前商场。
3. 仅凭“离某商场很近”或地址文本相似，不足以判定用户位于商场。
4. 门店属于商场的首选依据是父级 POI；人工审核可以覆盖自动归属并锁定字段。
5. 如果能够高置信度判断用户位于某个商场，响应包含 `currentMall`。
6. 前端先展示该商场内门店，再展示商场外一公里内门店。
7. 如果无法高置信度判断商场，不猜测，直接进入“附近一公里”模式。

### 9.3 附近模式的商场聚类

当无法可靠判断用户正处于某个商场时，附近结果采用语义聚类，而不是只按地图像素距离聚类：

1. 具有同一已确认 `mall_id` 的门店组成一个商场组。
2. 地图上每个商场组显示一个聚合标记，包含商场名和门店数量。
3. 点击商场聚合标记后，底部菜单定位并展开该商场组。
4. 底部列表按商场分组展示，商场组按用户到商场的距离排序。
5. 商场组内部的门店按用户到门店的距离排序。
6. 没有可靠商场归属的门店进入“周边街铺”组，仍按距离排序。
7. 不因门店彼此接近就推断它们属于同一商场；商场聚类只使用已确认归属。
8. 当地图缩放导致多个不同商场标记重叠时，可以再使用纯视觉点聚合，但视觉聚合不得改变底部列表的商场语义分组。

### 9.4 冷启动与刷新

- 查询网格的缓存有效期统一为三十天。
- V1 不因商场热度自动缩短缓存时间；需要提前更新时，由管理员触发刷新或通过人工纠错修正数据。
- 人工确认或锁定的字段不被自动刷新覆盖。
- 高德返回某门店消失时不立即删除；先标记待复核，避免短暂接口波动导致误删。

## 10. 门店纳入与分类规则

纳入：

- 奶茶店。
- 茶饮、果茶和其他以现制饮品为主的饮品店。
- 咖啡店。

排除：

- 普通餐厅，即使附带销售饮品或咖啡。
- 便利店、超市和仅销售包装饮料的商店。
- 以正餐为主、饮品只是附属品的场所。

分类输出统一为：

- `tea_drink`：奶茶、茶饮、果茶及其他现制饮品。
- `coffee`：咖啡店。

`all` 是前端聚合筛选，不是数据库分类。

实现时结合高德 POI 类型、关键词、品牌别名和排除规则分类。无法确定时先不展示，进入待复核状态。

## 11. 数据模型

### `brands`

- `id`
- `canonical_name`
- `aliases`
- `category`
- `created_at`
- `updated_at`

### `malls`

- `id`
- `provider`
- `provider_place_id`
- `name`
- `address`
- `location_gcj02`
- `location_wgs84`
- `boundary_wgs84`，可为空
- `last_seen_at`
- `last_verified_at`
- `manual_lock`

### `stores`

- `id`
- `provider`
- `provider_place_id`
- `brand_id`，可为空
- `name`
- `branch_name`，可为空
- `category`
- `address`
- `mall_id`，可为空
- `location_gcj02`
- `location_wgs84`
- `status`：`active`、`pending_review`、`possibly_closed`、`hidden`
- `first_seen_at`
- `last_seen_at`
- `last_verified_at`
- `manual_lock_fields`

默认不持久化完整 `source_payload`；若实施时确有审计或排错需要，必须先对照邮件许可确认允许保存的字段，并删除无关数据。

### `search_areas`

- `cell_id`
- `center_wgs84`
- `radius_meters`
- `last_fetched_at`
- `expires_at`
- `result_count`
- `fetch_status`

该表用于控制外部接口刷新，不保存用户的精确位置或行为轨迹。

### `correction_logs`

- `id`
- `store_id`，可为空
- `issue_type`：不存在、信息错误、遗漏门店、其他
- `details`
- `submitted_store_name`，遗漏门店时使用
- `submitted_address`，可为空
- `ip_hash`
- `status`：`pending`、`accepted`、`rejected`
- `created_at`
- `processed_at`，可为空

## 12. 匿名纠错与限流

- 普通用户不登录。
- 纠错表单只写入 `correction_logs`，不能直接更新正式门店。
- 服务端从可信代理头提取客户端 IP。
- 使用服务端私密盐对 IP 做不可逆哈希，不保存原始 IP。
- 提交前查询该 `ip_hash` 最近一次记录；五分钟内已有提交则拒绝，并返回剩余等待时间。
- 盐仅存在 Vercel 环境变量中。
- 第一版不加入验证码；如果出现滥用，再增加更严格的频率限制或验证码。
- 管理员在 Supabase 后台审核、修改门店并更新纠错状态。

## 13. 首页体验

已批准 A+B 混合布局：

- 地图是首页主视图。
- 顶部显示识别到的商场或“附近一公里”。
- 底部菜单默认露出最近门店。
- 用户向上滑动底部菜单后，地图缩小、列表展开。
- 分类标签固定在展开列表顶部：全部、茶饮、咖啡。
- “附近一公里”模式下，地图和底部列表同时按商场聚合；无法确认归属的门店列在“周边街铺”。
- 点击商场聚合标记时，列表展开对应商场；点击商场标题时，地图聚焦该商场。
- 点击地图标记时，列表滚动并突出对应门店。
- 点击列表门店时，地图聚焦对应标记。

门店卡片展示：

- 品牌与分店名称。
- 所属商场；未知时不显示。
- 距离。
- 地址。
- “复制品牌名”。
- “信息有误”。

复制后显示轻提示：“已复制，可前往微信搜索”。

## 14. 必须设计的页面状态

- 初次请求定位权限。
- 正在定位。
- 正在加载本地缓存。
- 正在从高德更新门店。
- 正常显示商场内门店。
- 正常显示附近一公里门店。
- 定位被拒绝：允许输入商场名或地址进行搜索。
- 定位不可用：同样进入手动搜索。
- 无结果：说明当前范围没有找到门店，并允许提交遗漏门店。
- 高德失败但数据库有旧数据：显示旧数据及更新时间。
- 高德失败且无缓存：显示可恢复错误并允许重试。
- 纠错提交成功。
- 纠错被五分钟限流。

手动搜索是建设者默认决策，因为拒绝定位不应让产品完全不可用。

## 15. API 边界

建议的服务端接口：

- `POST /api/nearby`：坐标放在 JSON 请求体中，返回商场、门店、缓存状态和更新时间。
- `GET /api/search-place?q=`：定位不可用时搜索上海商场或地址。
- `POST /api/corrections`：提交匿名纠错并执行 IP 限流。

统一错误响应包含稳定错误码、用户可读信息和是否可重试，不向客户端暴露供应商密钥或原始异常。

## 16. 安全与隐私

- 不保存用户精确位置。
- 不建立用户位置历史。
- 精确坐标不得出现在 URL、分析事件、错误消息或应用日志中。
- 应用日志不得记录 `/api/nearby` 请求体。
- Vercel、CDN 或其他基础设施可能依据各自政策生成短期网络与安全日志；产品数据库不得复制这些日志，部署时选择可用的最短保留设置。
- 高德 Key、Supabase Secret Key 和 IP 哈希盐只存于 Vercel 环境变量。
- 所有外部输入在服务端校验长度、类型和允许值。
- 纠错详情按纯文本处理，禁止渲染用户 HTML。
- Supabase 开启 RLS；正式表默认不允许匿名写入。
- 服务端日志不得输出密钥、原始 IP 或完整高德响应。

## 17. 性能与可靠性

- 页面先渲染地图骨架与底部菜单骨架，避免空白等待。
- 数据库命中时优先快速返回；后台刷新是否采用异步方式由实现计划根据 Vercel 运行限制决定。
- 同一网格的并发首次查询需要请求合并或数据库锁，避免重复调用高德。
- PostGIS 为门店位置建立空间索引。
- `provider + provider_place_id` 建立唯一约束。
- 高德超时、限额与无结果分别处理。

## 18. 验收标准

- 在支持定位的手机浏览器中，用户可以看到一公里内相关门店。
- 能识别商场时，商场内门店排在商场外门店之前。
- 不能识别当前商场时，具有可靠商场归属的附近门店在地图和列表中按商场聚合，未归属门店进入“周边街铺”。
- 商场聚类不能把仅仅位置接近、但没有可靠归属关系的门店强行归入商场。
- 普通餐厅不会因为销售饮品而默认进入列表。
- 地图与上滑门店列表互相联动。
- 标签可以在全部、茶饮和咖啡之间筛选。
- 复制品牌名成功并有明确反馈。
- 匿名纠错能写入数据库，但不能修改正式门店。
- 同一 IP 五分钟内第二次提交被拒绝。
- 定位拒绝后仍能通过商场或地址搜索使用产品。
- 高德接口失败时不会泄漏密钥或导致页面崩溃。
- Supabase 中不存在用户原始 IP 或精确位置日志。

### 建设者设定的可测质量门槛

以下是为避免“看起来能用”却无法验收而设定的 V1 默认门槛，实施计划可以在不降低核心体验的前提下细化测试方法：

- 选择至少 12 个代表性测试点，覆盖浦东、黄浦、静安、徐汇、长宁、闵行、宝山、杨浦、嘉定、青浦、松江和奉贤，包含商场内与非商场位置。
- 以同一时间、同一搜索半径下获得授权的高德查询结果为基准，相关奶茶、饮品和咖啡 POI 的召回率目标不低于 90%。
- 抽样结果中普通餐厅误入率低于 5%；无法判断的 POI 宁可进入待复核，也不直接展示。
- 对人工确认过的商场测试点，不允许把用户错误归入另一商场；无法确认时允许降级为“附近一公里”。
- 数据库命中的暖查询，服务端目标响应时间低于 1.5 秒；需要高德查询的冷查询，目标低于 5 秒。以上在正常网络和外部服务可用时测量。
- 首页首屏应先显示可交互骨架；外部数据延迟不能造成整页空白。

## 19. 留给建设者的选择
